## Why v2 exists

The accepted v1 wording counted `5 × 17 = 85` generation calls. Inspection of
the pinned `spec-wins` repository at commit
`776e799c7e0a24271e021aca2ea4b1c1b1f10017` showed three agentic task sessions,
not seventeen prompts:

- `t1_ratelimit` — 7 hidden grader checks;
- `t2_metrics` — 8 hidden grader checks;
- `t3_pipeline` — 2 hidden grader checks.

The 17 is the per-run grader denominator. A faithful run must give the model
one fresh conversation per task and preserve all intermediate tool/model turns.
Sending 17 synthetic prompts would measure a different instrument.

## Bounded execution

- Model: `qwen3.6-35b-a3b`.
- Runtime: the already hash-addressed dedicated thecodacus `llama.cpp`
  server, not Ollama and not the gateway.
- Benchmark source: the unmodified `spec-wins` checkout at the commit above;
  `hidden/`, `solutions/`, and `docs/answer-key.md` are never exposed to the
  model or copied into the writable task sandbox.
- Repetitions: 5 complete executions, with seeds
  `1000, 1017, 1034, 1051, 1068`, one seed per execution.
- Sessions per execution: exactly 3, in the order `t1`, `t2`, `t3`; each is a
  fresh model conversation containing the published preamble and exactly one
  published task block.
- Grader denominator: 17 checks per execution (`7 + 8 + 2`), reported per
  task and as a total.
- Reference generation budget: the published Qwen3.6 transcripts contain
  13, 27, and 26 assistant generations for `t1`, `t2`, and `t3` respectively.
  The v2 harness caps each corresponding session at those reference counts,
  for a maximum of 66 model generations per execution and 330 across the
  campaign. Tool calls do not count as model generations.
- No synthetic warm-up generation is included. Health, model, and VRAM checks
  are GET/read-only gates; any extra generation required by the harness is
  outside this authorization and blocks execution.

If a task reaches its cap without a final report, that task and execution are
`incomplete`; the harness must not silently turn an incomplete session into a
zero or a pass. The campaign result must disclose the actual generation count.

## Agent/tool contract

The model receives only the published preamble and one task block. The only
tool is a controlled `bash` wrapper that accepts the published `ssh lab
'cd ~/lab/<task> && ...'` shape and runs inside a dedicated writable sandbox.
The wrapper must fail closed on path escape, hidden/answer-key access, sudo,
network setup, or commands outside the task sandbox. The host performs grading
after the model reports completion; grader output is never returned to the
model.

Every model request records the effective seed, sampling options, context
size, runtime identity, task, session, request/response timestamps, response
metadata, and the complete raw response. The harness must use fresh messages
for each task and must not reuse a prior task's conversation state.

## Sampling and comparability boundary

The published repository does not expose the full sampling payload of the
historical Qwen3.6 run. v2 therefore fixes and records the effective sampling
payload used by this campaign, including seed, temperature, top-p/top-k and
context parameters. The result is a variance estimate for the pinned
`(model, runtime, benchmark commit, harness, sampling payload)` tuple. It is
not represented as a byte-for-byte reproduction of the historical request.

Runtime identity, model hash, execution context, metric definition and
sampling payload are mandatory in every record. Ollama and `llama.cpp` series
cannot be aggregated. Any comparison to the published 14/17 is labelled
`model-plus-runtime-and-protocol` unless the missing historical parameters are
independently recovered.

## Required outputs and stop rule

The campaign must persist:

1. five run manifests with the runtime/model/harness/prompt/task hashes;
2. three complete raw transcripts per run;
3. actual generation counts and per-request sampling metadata;
4. the five per-task grader matrices and totals;
5. an explicit variance and go/no-go record.

The P1 question is only whether this instrument/runtime pair has a measured
run-to-run spread. A result does not select a production candidate, authorize
watcher shadow mode, alter the gateway, or change Ollama.
